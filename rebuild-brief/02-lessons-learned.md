# สิ่งที่ควรระวังจากการตรวจสอบระบบเดิม

เอกสารนี้สรุปปัญหาจริงที่พบระหว่างตรวจสอบและแก้ไขระบบเดิมทีละหน้า (ไม่ใช่ปัญหาสมมติ) เพื่อให้ทีมที่สร้างระบบใหม่ไม่ทำผิดซ้ำ แต่ละข้อคือ pattern ของ bug ที่เกิดซ้ำมากกว่า 1 จุดในระบบเดิม

## 1. ฟอร์มที่มีช่อง input แต่ไม่เคยเชื่อมกับ state จริง

พบ 3 จุด: ฟอร์ม walk-in ของฟิตเนสเซ็นเตอร์ และฟอร์มจองยิมทั้งฝั่งนักศึกษา/แอดมิน — ช่อง "ชื่อ", "รหัสนักศึกษา", "สังกัด" เป็น input ที่หน้าตาเหมือนกรอกได้ แต่จริงๆ ถูก disable หรือผูกกับค่า default ที่ไม่มีใครเปลี่ยนได้ (เช่น `useState("TestWalkin")`, `useState("65010001")`, หรือข้อความ placeholder ที่หลุดเข้ามาอย่าง `"รอเชื่อม API typeA"`) ผลคือทุกการจองที่ผ่านฟอร์มเหล่านี้ถูกบันทึกด้วยชื่อ/รหัสปลอมเหมือนกันหมด โดยไม่มี error ใดๆ ให้เห็น

**แนวทางป้องกัน**: ทุกฟอร์มที่ submit ข้อมูลจริงต้อง code review โดยเช็คว่าทุก field ใน payload มาจาก state ที่ผู้ใช้แก้ไขได้จริง ไม่ใช่ default ที่ไม่มี `onChange` ไปอัปเดต

## 2. ชื่อฟิลด์ frontend ไม่ตรงกับที่ backend ส่งจริง

พบ 2 จุด: หน้า "ยืนยันตัวตน" และตารางสรุปใน KPI dashboard อ่านฟิลด์ `created_at` (snake_case) แต่ backend (TypeORM) ส่งเป็น `createdAt` (camelCase) เพราะ TypeScript ไม่ error เมื่ออ่าน property ที่ไม่มีอยู่ (ได้ `undefined` เฉยๆ) จึง compile ผ่านและรันได้ปกติ แต่คอลัมน์ "วันที่ทำรายการ" ว่างเปล่าทุกแถวมาโดยตลอด

**แนวทางป้องกัน**: ใช้ shared TypeScript type/interface ที่ generate หรือ sync จาก backend DTO จริง (เช่น openapi-typescript หรือ tRPC) แทนการพิมพ์ interface ซ้ำมือฝั่ง frontend เพื่อให้ compiler จับ mismatch แบบนี้ได้ทันที

## 3. คอมโพเนนต์ที่ถูก copy มาแก้ แต่ลืมแก้ label/ข้อความ

พบตารางจัดการ "ยกเลิกแบนผู้ใช้" (unban) ที่ copy โครงจากตาราง "อนุมัติการจอง" มาทั้งดุ้น รวมถึงหัวข้อ "Pending Approvals / Manage reservations waiting for admin approval" ที่ไม่เกี่ยวอะไรกับหน้านี้เลย และโค้ดส่วน reject ที่ comment ทิ้งไว้แต่ import ยังอยู่

**แนวทางป้องกัน**: การ copy component เพื่อทำ feature ใหม่ ให้ทำ checklist ตรวจ literal string ทั้งหมดในไฟล์หลัง copy และลบโค้ดที่ไม่ใช้ทิ้งทันทีแทนการ comment เก็บไว้

## 4. สถานะ/enum ถูกแม็ปซ้ำหลายที่ และมักหลุดค่าใดค่าหนึ่ง

`ApproveStatus` มี 8 ค่า (ดู `01-data-model.md`) แต่แต่ละหน้าที่ต้องแสดงสถานะ (ตาราง, chip, กราฟ) ต่างก็ประกาศ mapping label/สี ของตัวเองซ้ำ ทำให้อย่างน้อย 2 จุดลืมใส่ `rejected` — กราฟแนวโน้มการจองจึงนับไม่ครบ (booking ที่ถูกปฏิเสธหายไปจากกราฟเงียบๆ) และตารางหนึ่งแสดงคำว่า "rejected" ดิบๆ แทนภาษาไทย

**แนวทางป้องกัน**: ประกาศ status label/color map ไว้ที่เดียว (เช่น `constants/approveStatus.ts`) แล้ว import ใช้ร่วมกันทุกหน้า ไม่ copy-paste

## 5. "รหัสนักศึกษา" ไม่ได้ผูกกับบัญชี login — ต้องตัดสินใจแต่แรกว่าจะเอาแบบไหน

ระบบเดิม login ด้วยบัญชี mock (student01/staff01/admin) แต่ตอนจองสนามต้อง**พิมพ์รหัสนักศึกษาเอง**แยกต่างหาก ไม่เกี่ยวกับบัญชีที่ login อยู่ ผลคือหน้า "ประวัติการจองของฉัน" ไม่สามารถดึงข้อมูลอัตโนมัติจากบัญชี login ได้ ต้องให้ผู้ใช้พิมพ์รหัสนักศึกษาค้นหาเองทุกครั้ง (เหมือนระบบไม่รู้จักผู้ใช้)

**แนวทางป้องกัน**: ถ้าจะเชื่อมกับ SSO จริงในอนาคต (ตามที่ระบุใน `เอกสารข้อเสนอโครงการ_จองสนาม_ปรับปรุง.md`) ควรออกแบบให้ `student_id` มาจาก session/JWT ของผู้ใช้ที่ login อยู่โดยตรง ไม่ใช่ช่องกรอกอิสระ เพื่อให้ "ประวัติการจองของฉัน" ใช้งานได้จริงตั้งแต่วันแรก

## 6. Role-based access control ต้องทำทั้งฝั่ง frontend และ backend พร้อมกัน

ระบบเดิมไม่มีการจำกัดสิทธิ์เลยแม้แต่จุดเดียว — ทุก role เห็นเมนูและเข้าหน้า admin ได้หมดผ่าน URL ตรงๆ และเมื่อเพิ่ม guard ฝั่ง backend ภายหลัง ก็พบว่า frontend ไม่เคยแนบ JWT token ไปกับ request เลยสักครั้ง (เพราะไม่เคยมี endpoint ไหนบังคับให้ login มาก่อน) ทำให้ทุกฟีเจอร์ admin เกือบพังทันทีที่เริ่ม enforce สิทธิ์

**แนวทางป้องกัน**: ตัดสินใจเรื่อง role/permission ตั้งแต่ต้น และทำ auth guard (route-level ฝั่ง frontend + endpoint-level ฝั่ง backend) พร้อมกับ auth token attachment (เช่น axios interceptor) ตั้งแต่ sprint แรก ไม่ใช่ผูกทีหลัง

## 7. capacity แบบ "1 คนต่อสนาม" กับ "หลายคนต่อสนาม" ต้องออกแบบแยกกันจริงจัง ไม่ใช่ hack ทีหลัง

ยิมเป็นสนามเดียวในระบบที่รับได้ 30 คนพร้อมกันต่อช่วงเวลา ส่วนสนามอื่นรับได้ 1 การจองต่อช่วงเวลา ระบบเดิมมีฟอร์มจองยิมโดยเฉพาะที่ตั้งใจรองรับ capacity แบบนี้อยู่แล้ว แต่ระหว่างพัฒนามีจุดที่ route ไปเรียกฟอร์มทั่วไป (แบบ 1 คน) แทนโดยไม่ได้ตั้งใจ ทำให้ยิมกลายเป็น "จองได้คนเดียวต่อชั่วโมง" ไปพักหนึ่งโดยไม่มีใครสังเกต เพราะแอปยัง compile และรันได้ปกติ

**แนวทางป้องกัน**: เขียน integration test ที่ยืนยันพฤติกรรม capacity ของสนามแบบกลุ่ม (ยิม) แยกจากสนามแบบเดี่ยว เพื่อให้ regression แบบนี้ถูกจับได้อัตโนมัติ ไม่ต้องรอคนมาเทสมือ

## 8. การ seed ข้อมูลภาษาไทยผ่าน terminal/script บนเครื่อง Windows อาจเพี้ยน

พบว่าการยิง API ผ่าน `curl` จาก PowerShell/Git Bash บนเครื่อง Windows บางครั้งทำให้ข้อความภาษาไทยที่ฝัง argument ถูกเก็บเป็นตัวอักษรผิด (mojibake) ทั้งที่ข้อมูลที่มาจากเบราว์เซอร์จริง (ผ่าน axios/JSON) ไม่มีปัญหานี้เลย

**แนวทางป้องกัน**: seed ข้อมูลทดสอบผ่านสคริปต์ (Node/TypeScript) ที่รันในสภาพแวดล้อม UTF-8 ชัดเจน แทนการยิง curl ตรงจาก shell ของ Windows หรือ seed ผ่าน UI จริงเมื่อเป็นไปได้

## 9. หน้าตารางข้อมูลควรมี loading/empty state ตั้งแต่แรก

หลายหน้าไม่มี loading indicator ระหว่างรอ API และไม่มีข้อความ "ไม่พบข้อมูล" เมื่อผลลัพธ์ว่าง ทำให้ตอนโหลดข้อมูลช้าจะเห็นข้อความ "ไม่พบข้อมูล" กระพริบขึ้นมาก่อนข้อมูลจริงจะมา ดูเหมือนระบบพัง

**แนวทางป้องกัน**: ทำ pattern มาตรฐาน (loading spinner + empty state component) ไว้ตั้งแต่แรก แล้วใช้ร่วมกันทุกตาราง แทนที่แต่ละหน้าจะเขียนเองแยกกัน
