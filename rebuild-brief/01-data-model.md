# Data Model (สรุปจากระบบเดิม)

เอกสารนี้สรุปโครงสร้างข้อมูลจริงที่ระบบเดิมใช้งาน (ตรวจสอบจากโค้ด backend จริง ไม่ใช่จากเอกสารข้อเสนอโครงการ) เพื่อให้ผู้พัฒนาใหม่เริ่มออกแบบฐานข้อมูลได้เร็วขึ้น และไม่พลาดกรณีพิเศษที่ระบบเดิมต้องแก้ปัญหามาแล้ว

## Entities หลัก

### ReservationSlot (การจอง — ระดับ "ช่วงเวลาที่จองจริง")
นี่คือ entity ที่เก็บสถานะจริงของการจองแต่ละช่วงเวลา แยกจาก `Reservation` เพราะการจองครั้งเดียวเลือกได้หลายช่วงเวลา และแต่ละช่วงเวลาอาจถูกอนุมัติ/ปฏิเสธไม่พร้อมกัน

| ฟิลด์ | ชนิด | หมายเหตุ |
|---|---|---|
| id | int | |
| date | string (YYYY-MM-DD) | |
| approve_status | enum `ApproveStatus` | ดูด้านล่าง |
| reason | string, nullable | เหตุผลเวลาปฏิเสธ/ไม่มาใช้บริการ |
| is_available | boolean | |

### BookingStatus (วัตถุประสงค์การจอง — lookup table)
ตัวอย่างค่า: จองเพื่อออกกำลังกาย, จองเพื่อการเรียนการสอน, จองเพื่อกิจกรรม, ปิดปรับปรุง, มหาวิทยาลัยปิด, walk-in

## Enum: ApproveStatus (สถานะของ ReservationSlot)

นี่คือสถานะจริงที่ระบบเดิมใช้ — **ต้องรองรับครบทั้ง 8 ค่านี้ในทุกหน้าที่แสดงสถานะ** (ระบบเดิมมี bug ที่บางหน้าลืมใส่ `rejected` ทำให้ข้อมูลหายไปจากกราฟ/ตาราง โดยไม่มี error ใดๆ):

| ค่า | ความหมาย | ใครเป็นคนตั้งสถานะนี้ |
|---|---|---|
| `pending` | รอ admin อนุมัติ | ค่าเริ่มต้นตอนจอง |
| `approved` | admin อนุมัติแล้ว รอมาใช้งานจริง | admin |
| `rejected` | admin ปฏิเสธคำขอ | admin (ต้องระบุเหตุผล) |
| `cancel` | ผู้จองยกเลิกเอง | ผู้จอง |
| `success` | มาใช้งานจริงและยืนยันสำเร็จ | admin (หลังตรวจสอบหน้างาน) |
| `no_show` | อนุมัติแล้วแต่ไม่มาใช้งาน | admin (ต้องระบุเหตุผล, มีผลต่อ ban_count) |
| `close` | ปิดสนามช่วงนั้น (ปรับปรุง/มหาวิทยาลัยปิด/กิจกรรม) | admin |
| `walk-in` | คนที่มาใช้บริการหน้างานโดยไม่ได้จองล่วงหน้า (เฉพาะยิม) | เจ้าหน้าที่หน้างาน |

## กฎเชิงธุรกิจที่ต้องคงไว้

1. **สนามทั่วไป (capacity = 1)**: หนึ่งช่วงเวลา/หนึ่งสนาม จองซ้ำไม่ได้ถ้ามีคน `pending`/`approved`/`success`/`close` อยู่แล้ว
2. **ยิม (capacity = 30)**: หนึ่งช่วงเวลา รับได้พร้อมกันหลายคนจนกว่าจะครบ 30 — ต้องนับจำนวนคนต่อช่วงเวลา ไม่ใช่เช็คแค่ "มี/ไม่มี" การจอง
3. การจองหนึ่งครั้ง (`Reservation`) เลือกได้หลายช่วงเวลาพร้อมกัน แต่ละช่วงเวลาต้องอนุมัติ/ปฏิเสธแยกกันได้ (บาง slot อนุมัติ บาง slot ปฏิเสธ ในคำขอเดียวกัน)
4. การยกเลิกต้องระบุ `date` + `timeSlot.id` + `reservation.id` ให้ครบ เพราะ `ReservationSlot` ไม่มี unique key เดี่ยวที่ frontend รู้จักโดยตรง
